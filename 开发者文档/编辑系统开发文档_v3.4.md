## 一、项目背景与技术路线

将原本高度耦合、平铺在单个文件中的编辑脚本，进行**深度模块化降维拆解**，最终实现了一个健壮、可插拔的富文本排版与涂鸦引擎。

**核心技术路线：**
1. **纯粹的模块化外部引用**：摒弃面条代码，彻底切分为 `EditorCore`，`RichTextToolbar`，`BoxManager`（文本框），`ImageManager`（图片），`HistoryManager`，`PersistenceLayer` 及 `DoodleRuntime` **7 大模块**，严格按顺序加载。这使得导出的 HTML 极为干净。
2. **底层 DOM 精细化介入**：抛弃了部分行为不可控的 `document.execCommand`（如 `fontSize` 会生成老迈的 `<font size="..">`，下划线无法控制颜色等），改为全盘接管 Span 的包裹、切割与剥离操作。
3. **文本/图片职责分离（2026-05-12）**：`editor-text-manager.js`（文本框专用）和 `editor-images.js`（图片专用）从原先的编辑模块中拆分独立。`BoxManager` 只管理文本框的创建、拖拽、删除；`ImageManager` 接管图片框的创建、拖拽、八爪鱼缩放和删除。两者共享同一套 `.box-controls` 控件条与 `.rs-handle` 缩放点视觉体系，但实现上完全解耦。
4. **双轴互不干涉架构**：DOM 结构树编排（文字、高亮、拖拽）与独立 Canvas 层板（Doodle涂鸦手写）分层独立，用指针事件和 CSS 穿透控制优先级。

### 2.1 2026-04-25 普通页面隐藏型富文本通道已经全局化

- 普通组件文本已经纳入新的二级步进体系：只要片段位于普通页面、普通 `[data-edit-id]` 根块内，就可以通过 `page-richtext-fragment-toolbar` 被标记为 `data-fragment-step="true"` authored fragment。
- 顶部主编辑工具栏与隐藏型标注通道已经明确分成两类语义：
    - 顶部工具栏添加的普通富文本，放映时直接显示；
    - 选区浮动工具条添加的隐藏型标注，放映 / 涂鸦时默认隐藏，需要 hover、右键 reveal、或 `←→` 步进才显现。
- 普通页隐藏标注不再按“整页文本根块自己步进”工作，而是由 `page-richtext-annotation-runtime.js` 把片段归属到最近的一级焦点宿主：卡片、统计卡、时间线、代码窗、图表、表格、图片块、双色条、内容块，以及 `summary-trigger` 都可以成为宿主。
- 作者态与放映态继续分离：编辑模式下片段默认全显；放映态下只恢复 authored 结构，不保留临时 reveal 游标。导出 HTML 与 `.annotations.js` 时会继续剥离 `qa-fragment-visible`、`data-fragment-manual-reveal` 一类临时课堂状态。

### 2.2 2026-04-25 选区工具条、持久化与运行时协同

- 现在存在三套互不混淆的编辑浮层：
    - 顶部主工具栏：通用排版；
    - `qa-annotation-toolbar` / `qa-note-fragment-toolbar`：只服务 `quiz-annotation`；
    - `page-richtext-fragment-toolbar`：只服务普通页面隐藏型标注。
- `selectionchange` 仍然只承担“追踪选区”职责；普通页和 quiz 页的浮动工具条都必须等到本次拖选完成后的 `pointerup` 再刷新，避免拖选过程中提前弹出、抢焦点或误触。
- `AnnotationStore` 的读取路径继续保持双轨：`file://` 走脚本注入恢复，HTTP(S) 走 sandbox iframe；但普通页面隐藏型标注现在也复用了同一个 `.annotations.js` 侧车协议，不再只服务 quiz。
- `editor-rich-text.js` 在作者态新增 / 删除普通页 fragment 后，会调用 `PageRichTextAnnotationRuntime.refreshSlide(slide)` 与 `refreshInteractionQueueForCurrentSlide()`，同步页面是否具备普通页宿主资格、以及宿主是否需要自动注册为 `page-richtext-host`。
- 页面中只要存在 `quiz-annotation`，普通页面隐藏型标注 runtime 就会整页早退：作者态仍可编辑，但放映 / 涂鸦态下的 hover、右键 reveal、左右键步进不会和 quiz 内部规则叠加。
- 音效层仍不属于编辑器公共工具链；编辑模式通过 `AudioRuntime.isEnabled()` 全局静音，确保文本编辑、拖拽和局部富文本操作不会被放映提示声打断。

## 三、踩坑实录与深度排障指南 (Blood & Tears)

在开发 v3.0 到 v4.0 的深水区，我们遭遇了多个极其隐蔽的浏览器渲染与选区底层机制陷阱。现作为“必读踩坑指南”记录如下。

### 坑位 1：格式叠加移除时的“全盘尽毁” (The Overzealous Cleaner)
**问题表现**：当用户选中一段文本，同时给它打上带有颜色的 `下划线` 和 `删除线` 时，它们在 DOM 中被合并记录为 `<span style="text-decoration: underline line-through">`。此时如果用户尝试“取消下划线”，旧版清理代码 `.removeProperty('text-decoration')` 会把两个线**同时删掉**。
**解决方案**：不要用浏览器原生 API 删属性。必须获取属性字符串，用**正则匹配切割** (`split(/\s+/)`)，精准剥离被取消的具体词元（比如剔除 `line-through`，保留 `underline`），再重新 `.join(' ')` 拼装回去。这是一场微型外科手术。

### 坑位 2：致命的 DOM 吸附与蔓延缺陷 (The "C" Infection)
**问题表现**：当 `A` 和 `B` 在前期被赋予了 `<span 下划线>` 之后，此时页面结构为 `[AB] C`。当用户框选 `ABC` 全体，试图新增全体“删除线”时，系统却把本应清白的 `C` 拉入了外层的下划线作用域中，导致 C 意外感染了下划线。
**原理解析**：
为了解决“提取内部选区会导致外层容器残留”的问题，我们曾设计了一个自以为巧妙的 `_splitDecoSpanAtRange`（在选区边界处强制物理拦腰斩断父元素的解包函数）。
**最大的错觉在于它被滥用了**。当我们在做“向外**扩充**大样式”时，强制执行这个物理切割，它在原生底层的 `range.extractContents()` 阶段，将原本在外面的无辜字符 `C` 一同卷入，并在重新缝合时硬生生地将其包入了先前的内层环境里。
**最终防波堤防（解决方案）**：
我们在切割逻辑前加入了一道神圣的门槛检查 `if (allDecorated)`：
如果当前操作是在**应用/扩充**跨界样式（而非取消），绝对禁止动手斩断边界。直接让原生的 `extractContents` 与 `insertNode` 接手处理。他们能够完美在公共父级最高处包裹新壳，绝对不会发生吸附蔓延。

### 坑位 3：神秘消失的 `removeUnderline`
**问题表现**：重构完成后，点击下划线调色板最下方的“X”按钮毫无反应。
**原理解析**：在庞大单体转变为 7 个文件的架构跃迁中，由于人脑的物理内存溢出，`removeUnderline` 的执行体意外缩成了一个空壳，只发出了历史记录的信号，没有真实进行 DOM 的拔除操作。
**解决方案**：重新接回完整的抽取生命周期（提取 `extractContents` → 执行清理 `_cleanDecoration` → 洗净后原路裸插回 `insertNode`）。

### 坑位 4：字号修改的 `execCommand('fontSize')` 古早陷阱
**问题表现**：调用原生的更改字号指令，会使得 DOM 里布满 `<font size="1">` 等上世纪的废弃标签，不但不支持 `px` 等现代单位伸缩，还会无情碾压响应式外围 CSS。
**解决方案**：这是彻底抛弃 `execCommand` 的导火索。自己建立选区剥离循环，在提取出来的 fragment 外层包裹带有绝对像素 `style="font-size: XXpx"` 的原生 HTMLSpanElement。

### 坑位 5：失去焦点的工具栏导致选区消逝
**问题表现**：一旦点击毛玻璃工具栏内的某些颜色色板，编辑器主视窗失去了焦点，再去获取 `getSelection()` 就只剩下了 null。
**解决方案**：构建持久的“幽灵选区”缓存。全局监听 `selectionchange`，只要选区是在可编辑块内就立即捕获备存进 `savedRange`。所有工具栏操作使用 `pointerdown` 并且强制 `e.preventDefault()` 组织失焦漂移；在执行操作前，永远第一步执行 `this.restoreSelection()` 强行拉回缓存的光标靶点。

### 坑位 6：DOM 变动引发的入场动画无限狂欢 (The DOM Re-mount Loop)
**问题表现**：前期每次进出编辑模式，或执行 `Ctrl+Z` 撤销时，所有的幻灯片内组件都会重新播放一遍入场动画，导致排版发生剧烈位移闪烁。即使给 `.editor-mode .slide *` 挂载 `animation: none !important` 甚至是冻结类 `.no-anim`，在退出编辑模式那瞬间，动画仍然像没事人一样重播！
**原理解析**：
最初，我们在刚进入编辑模式时，动态向 DOM 里 `insertBefore` 插入了原生隔离框 `.native-edit-wrap`，并在退出时将包裹框剥离（用物理插拔方法试图还原出厂纯净设定）。浏览器对于这种物理级别的拔出与重插，不可避免地将其视为元素“新挂载（Re-mount）”。而恰逢退出时移除了 `.editor-mode` 类，这导致防线失效，原生主题 CSS 的高度特异性动画 `.slide.active .anim-*` 瞬间接管，把组件全屏重绘了一遍。
**解决方案（零 DOM 变化红线原则）**：
1. **停止反复插拔 DOM**：包裹隔离框 `.native-edit-wrap` 改为**纯幂等一次性永久注入**。在页面存续期间仅第一次被建立并永远存在，进出编辑模式仅仅做纯粹的状态切换 `classList.toggle('editor-mode')`，彻底斩断重新挂载循环。
2. **改抹杀为降维暂停（Paused 降维打击）**：将极具破坏性的 `animation: none` 修正为以柔克刚的 `animation-play-state: paused`。这样元素仅是被冻结在了最终排版阶段，卸下编辑模式时，动画只是从“已完成”形态恢复运作，失去了重头再来的条件。
3. **JS 瞬间终结重绘**：针对初次注入时以及撤销/重做引发的重绘震荡，采用了 Web Animations API 的大杀器：调用 `slide.getAnimations({ subtree: true }).forEach(a => a.finish())`，物理剪短动画的播放时间轴，将界面在毫秒级别稳固死。

## 四、各引擎设计总则

### 4.1 历史引擎 (HistoryManager) 的超轻量化
鉴于之前的无限历史栈会导致包含几百张 Base64 图片的 DOM 直接撑爆浏览器堆内存（Heap Out of Memory）。现在变更为：
- **按页拆分**：根据 slideIndex 进行独立压栈，退出前页即刻休眠并定格记录。
- **纯内存级**：切断了与 `localStorage` 混排的复杂交叉逻辑。页面刷新即清空历史。对于真正的文件级保存，单凭 `Ctrl+S` 的导出即可。

### 4.2 导出清洗机 (PersistenceLayer)
在 `exportCleanHTML` 中，绝不能对内存里正在工作的活体 DOM 进行诸如 `removeChild` 的移除把手操作！
标准清洗范式为：
1. `cloneNode(true)` 生成不干扰真身的完整克隆体。
2. 对克隆体使用 `querySelectorAll` 抹除类似于 `.floating-controls` 的挂载小组件以及所有注入编辑工具的脚本。
3. 把清纯的文本输出为 Blob 回馈用户。
