## 一、系统定位

音效模块负责为课件运行时提供一条**轻量、可复用、可静音**的提示声通路。

它不负责配乐，不负责时间轴混音，也不负责把“每个组件该在什么时候响”写死在全局放映器里。当前架构明确拆成两层：

- `assets/audio-runtime.js`：全局音效总线。负责 cue 名称注册、音频资源映射、播放路径选择、模式静音开关与调试状态。
- `assets/quiz-annotation-audio.js`：组件适配层。负责把答题与批注组件里的“片段前进 / 片段后退 / hover 提示”翻译成对全局 cue 的调用。

这套拆分的核心目标有三个：

1. 组件层只关心“我要播什么 cue 名称”，不关心底下具体是 mp3、flac 还是未来换素材。
2. 编辑模式必须全局静音，避免排版与课堂放映提示声互相打架。
3. 独立课件常常直接以 `file://` 打开，因此播放链路必须兼容本地文件安全限制，不能把能力完全押在 Web Audio API 上。

## 二、架构总览

```text
┌────────────────────────────────────────────────────────────┐
│                    AudioRuntime（全局音效总线）             │
│  cueDefinitions │ isEnabled │ register/playComponentCue    │
└──────────────────────┬─────────────────────────────────────┘
                       │
        ┌──────────────┴──────────────┐
        │                             │
┌───────▼────────────────┐   ┌────────▼───────────────────────┐
│  全局 cue 调用          │   │  组件 cue 适配层               │
│  playGlobalCue()       │   │  QuizAnnotationAudio          │
│  例：focus-shift       │   │  fragment-step / fragment-hover│
└──────────────┬─────────┘   └────────┬───────────────────────┘
               │                       │
               └──────────────┬────────┘
                              │
                   ┌──────────▼──────────┐
                   │  sound/ 实体音频资源 │
                   │  pop / whoosh / hover│
                   └──────────────────────┘
```

当前仓库里，答题与批注组件已经接上这条总线；其他组件若未来需要音效，也应走同一套 `registerComponentCue()` / `playComponentCue()` 协议，而不是各自私有化一份播放器。

## 三、AudioRuntime 设计

### 3.1 cue 预置表

`audio-runtime.js` 只维护“cue 名称 -> 实体音频资源”的映射。当前内置 4 个预置：

| cue 名称 | 资源文件 | 默认增益 | 当前用途 |
|---------|----------|----------|----------|
| `focus-shift` | `assets/sound/pop.mp3` | 2 | 批注焦点切换 |
| `fragment-swoosh` | `assets/sound/whoosh.mp3` | 2 | 片段前进揭示 |
| `fragment-swoosh-back` | `assets/sound/whoosh_back.mp3` | 2 | 片段后退回收 |
| `ui-hover` | `assets/sound/annotation_hover.flac` | 5 | 片段 hover 提示 |

组件层只应引用这些 cue 名称，而不应直接硬编码音频文件路径。

### 3.2 全局 API

当前暴露到 `window.AudioRuntime` 的核心接口如下：

- `isEnabled()`：判断当前模式下是否允许播放。
- `getCueDefinition(name)`：返回某个 cue 的只读定义。
- `playPreset(name)`：直接播放一个全局预置 cue。
- `playGlobalCue(name)`：语义化别名，当前内部仍走 `playPreset()`。
- `registerComponentCue(componentName, cueName, handler)`：给某个组件注册 cue 处理函数。
- `playComponentCue(componentName, cueName, payload)`：播放组件级 cue。
- `getDebugState()`：输出最近一次播放的 cue 名、播放器类型、错误信息与当前协议。

### 3.3 模式开关

音效总线当前只识别三种运行态：

- 编辑模式：静音。
- 普通放映模式：允许播放。
- 涂鸦模式：允许播放。

编辑模式静音并不是由每个组件各自判断，而是由 `AudioRuntime.isEnabled()` 统一拦截。这样可以保证以后新增组件时不会漏掉静音规则。

### 3.4 HTTP(S) 与 file:// 的双路径播放

这是当前音效模块最关键的工程决策之一。

在 HTTP(S) 或本地服务场景下，`audio-runtime.js` 优先走 **Media Graph 路径**：

- 通过 `AudioContext` + `createMediaElementSource()` + `GainNode` 做真实增益。
- 这样可以把 2x / 5x 的 cue 放大量化成统一的数字增益。

但独立课件通常直接双击打开，运行在 `file://` 协议下。此时把本地媒体接入 Web Audio API，在部分浏览器里会直接抛 `SecurityError`，或者表现成“看起来播放了但实际上静音”。

因此本地模式必须回退到 **fan-out 普通音频并发** 路径：

- 根据目标增益拆成若干个普通 `Audio` 实例。
- 多路并发播放，近似实现“放大后的响度”。
- 优先保证“能听见”，而不是追求最理想的数字增益链路。

调试时可以用 `AudioRuntime.getDebugState()` 判断最近一次播放走的是 `media-graph` 还是 `fan-out`。

## 四、QuizAnnotationAudio 组件适配层

`quiz-annotation-audio.js` 是一层非常薄的翻译层，它只做两件事：注册 cue，以及在组件代码里提供更语义化的调用入口。

### 4.1 注册协议

组件名固定为 `quiz-annotation`，当前注册了两个 cue：

- `fragment-step`
  - `direction === 'forward'` -> `fragment-swoosh`
  - `direction === 'backward'` -> `fragment-swoosh-back`
- `fragment-hover`
  - 固定映射到 `ui-hover`

### 4.2 对外调用接口

当前暴露到 `window.QuizAnnotationAudio` 的接口有：

- `registerCues()`
- `playFragmentStep(payload)`
- `playFragmentHover(payload)`

### 4.3 hover 节流

hover 声会按 `linkId` 做 160ms 冷却节流：

- 同一个锚点在极短时间内反复触发 hover，不会连续刷屏式发声。
- 不同 `linkId` 之间仍可正常各自触发。

这条节流既适用于普通放映模式，也适用于 doodle hit-test 代理出来的 hover 通路。

## 五、运行时触发点

当前与音效模块真正联动的地方主要集中在答题与批注运行时：

### 5.1 顶层焦点切换

当当前激活批注从一个气泡切到下一个气泡时，`quiz-annotation-runtime.js` 会调用：

```javascript
window.AudioRuntime.playGlobalCue('focus-shift')
```

这个声音属于“顶层焦点变化”，不依赖具体片段是否已经展开。

### 5.2 片段揭示与回退

当当前焦点气泡内部的 `data-fragment-step="true"` 片段前进或后退时，运行时会调用：

```javascript
window.QuizAnnotationAudio.playFragmentStep({ direction, reason })
```

其中：

- `forward` 播放 `fragment-swoosh`
- `backward` 播放 `fragment-swoosh-back`

### 5.3 hover 提示

当鼠标悬浮到可触发片段发现的 `.text-anchor` / `.answer-anchor` 上时，运行时会调用：

```javascript
window.QuizAnnotationAudio.playFragmentHover({ linkId, ... })
```

为了避免旧版“持久化标记导致普通放映模式静音”的问题，hover 监听是否已绑定现在只记录在运行时私有属性 `__qaFragmentHoverAudioBound` 上，不再写回 DOM 属性。

### 5.4 doodle 模式下的间接触发

在涂鸦模式中，hover / 右键揭示并不是直接落在底层 DOM 上，而是先经过 doodle hit-test 解析，再由 quiz-annotation 代理触发。音效模块对这一层完全无感，只要最终有人调用 `playFragmentHover()` / `playFragmentStep()` 即可。

## 六、HTML 引用顺序

当且仅当课件里使用了 `.quiz-annotation` 组件时，建议按下面顺序加载相关脚本：

```html
<script src="./assets/slides-runtime.js"></script>
<script src="./assets/audio-runtime.js"></script>
<script src="./assets/annotation-store.js"></script>
<script src="./assets/quiz-annotation-audio.js"></script>
<script src="./assets/quiz-annotation-runtime.js"></script>

<script src="./assets/editor-utils.js"></script>
<script src="./assets/editor-persistence.js"></script>
<script src="./assets/editor-history.js"></script>
<script src="./assets/editor-box-manager.js"></script>
<script src="./assets/editor-rich-text.js"></script>
<script src="./assets/editor-core.js"></script>
<script src="./assets/doodle-runtime.js"></script>
```

顺序说明：

- `audio-runtime.js` 必须先于 `quiz-annotation-audio.js`，因为组件适配层要在加载时向全局总线注册 cue。
- `quiz-annotation-runtime.js` 必须晚于 `annotation-store.js` 与 `quiz-annotation-audio.js`，因为它会直接调用这两层能力。
- 编辑器与涂鸦模块继续保持在 quiz 运行时之后加载，沿用原有依赖顺序。

## 七、测试与排障

### 7.1 当前测试覆盖

仓库里已有专项测试：

- `testing/tests/audio-runtime.test.js`
- `testing/tests/quiz-annotation-runtime.test.js`
- `testing/tests/slides-runtime.test.js`

这些测试当前覆盖了：

- cue 定义是否存在；
- HTTP(S) / `file://` 双路径回退是否成立；
- 组件适配层是否正确把 fragment step / hover 翻译成 cue 播放；
- 放映运行时是否在正确时机调用这些接口。

### 7.2 常见排障点

1. 普通放映模式 hover 没声音，但 doodle 模式有声音。
原因通常是旧版把“已绑定 hover 监听”写成了 DOM 持久化属性。当前正确做法是只用运行时私有标记。

2. 本地双击打开的课件完全静音。
优先检查是否误删了 `fan-out` 回退逻辑，或者把播放强行绑死在 `createMediaElementSource()` 路径上。

3. 编辑模式里操作文字时也在响。
说明模式静音入口被绕过了。应统一走 `AudioRuntime.isEnabled()`，而不是让组件自己判断是否要播。

4. 组件想新增音效。
不要直接 new 一套播放器。先把资源接到 `audio-runtime.js` 的 `cueDefinitions`，再通过 `registerComponentCue()` 暴露给组件层。

一句话总结设计哲学：**全局总线只管“有什么声音、现在能不能响”，组件适配层只管“什么时候触发哪一个 cue”。**
